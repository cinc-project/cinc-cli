# Integration tests against cinc-server-ng and cinc-server-erlang

**Date:** 2026-09-23
**Module:** `github.com/cinc-project/cinc-cli/integration` (new nested module)

## Goal

Run one set of end-to-end tests of the `cinc` binary against two servers:

- **cinc-server-ng**, the in-memory Go server, on every pull request, every
  push to `main`, and every release tag (a release does not publish binaries
  until the suite passes).
- **cinc-server-erlang**, the CINC Server Erlang stack (erchef), started on
  demand in AWS by a developer, to confirm the CLI matches the server that
  users actually run.

This follows the design `cinc-api` adopted on 2026-09-22. Its first
cinc-server-erlang run found several request-format bugs that its unit tests
and cinc-server-ng both accepted. The CLI builds every request through
`cinc-api`, but it composes those calls into workflows (policy push, cookbook
upload, key rotation, ACL edits, data bag secrets) that only an end-to-end run
against erchef proves.

The shared suite **replaces** `test/acceptance`. Everything it covers today
moves into the suite and runs against both servers; `test/acceptance`, its
cinc-zero download harness and the `Acceptance (cinc-zero)` check are removed
once the port is complete.

## Decisions

| Topic | Decision |
|---|---|
| Test sharing | One suite, two targets. Each test is written once. |
| Layout | One Go module (`integration/`) with packages `suite`, `cincserverng`, `cincservererlang`, plus `terraform/`. |
| What runs | The real `cinc` binary, built once per run from the repository root module (`go build -C <root>`), so its dependencies match a release build, not the integration module's. |
| cinc-server-ng | Imported in process (`server.New`) and pinned in `integration/go.mod`. Dependabot bumps it; no download or checksum code. |
| Naming | The targets are always "cinc-server-ng" and "cinc-server-erlang", never "real" or "cinc-zero". |
| Who runs the erlang suite | A developer, locally, with their own AWS credentials. No GitHub workflow. |
| Network | Public Elastic IP; security group allows 443 from the caller's /32 only; no SSH. |
| TLS | Throwaway CA generated by Terraform. The CLI trusts it through `trusted_certs_dir`, a knife-compatible config key this work adds. Never `:verify_none`. |
| Admin | cinc-server-ng: the bootstrap `pivotal`. cinc-server-erlang: a server-admin who is an admin of both test orgs; pivotal's key never leaves the instance. |
| ACLs | cinc-server-ng runs with ACL enforcement on, as erchef always does. |
| Secrets | None committed. AWS credentials come from the environment or profile; generated keys live only in local, gitignored state and output files. |
| Coverage guard | Every shipped leaf command is covered by a suite case or exempt with a reason, enforced by a test that walks the live cobra tree. Replaces `coverage_manifest.toml`. |

## Layout

```
integration/
  go.mod                       replace ../ ; requires cinc-server-ng
  suite/                       shared cases, helpers, coverage guard
  cincserverng/                cinc-server-ng target (CI)
  cincservererlang/            cinc-server-erlang target (ad hoc)
  terraform/                   AWS stack for cinc-server-erlang
    .out/                      generated target.json, admin.pem, ca.pem (gitignored)
  run-cinc-server-erlang.sh    apply, test, destroy
  README.md
```

## Section 1: shared suite (`integration/suite`)

### Target

```go
type Target struct {
    Name       string            // "cinc-server-ng" | "cinc-server-erlang"
    ServerURL  string            // base URL, without /organizations/...
    Org        string            // org the tests create objects in
    OtherOrg   string            // second org the admin belongs to
    Admin      string            // user the CLI signs as
    KeyPath    string            // admin private key
    CACertPath string            // CA to trust; "" for plain HTTP
    Gaps       map[string]string // case name -> reason
}

func Run(t *testing.T, tgt Target)
```

`Run` runs every case as a parallel subtest named `<family>/<case>`. A case
listed in `Gaps` is skipped with its reason. A gap that names no case, or has
an empty reason, fails the run.

### Driving the CLI

Each case gets its own `cli` helper: a temporary `HOME` whose
`~/.cinc/credentials` has a `default` profile for `Org` and an `other` profile
for `OtherOrg`, signing as `Admin`, with `trusted_certs_dir` pointing at a
directory holding `CACertPath`. Nothing reads the developer's real
`~/.cinc` or `~/.chef`. The helper runs the binary with that `HOME`, returns
stdout and stderr, and has variants that expect success, expect a failure
exit, add environment variables, feed stdin, or attach a pseudo-terminal (for
the first-run setup prompts).

Cases assert on `--format json` output wherever a command offers it, so a
table layout change never breaks a server test.

### Cases and coverage

Each case declares the leaf commands it exercises:

```go
type testCase struct {
    name   string   // "<family>/<case>"
    covers []string // e.g. {"node create", "node show", "node delete"}
    run    func(t *testing.T, tgt Target, c *cli)
}
```

The coverage guard (`suite/coverage_test.go`, plain `go test`, no server)
walks `cmd.NewRootCmd()` and fails when a leaf is neither covered by a case
nor listed in `exempt` with a reason, or when a `covers` or `exempt` entry
names a command that does not exist. Candidates for `exempt`: the
`supermarket` commands (a public service, covered by httptest unit tests) and
`node ssh` and `node bootstrap` unless a case can run them against a
container. While the port is in progress, each family file carries a
`pending` list the guard also accepts; the family's port PR empties it.

Families, one file each: nodes (including run lists, tags, status,
environment and policy assignment), search and explore, roles, environments,
clients, users, keys, groups, orgs (members and invitations), ACLs for every
noun, data bags and secrets, cookbooks, policies and policy groups, and CLI
behaviour (config create and validate, first-run setup and chef credential
migration, profiles, chef-compat environment variables, output formats,
error messages for 401, 403, 404 and 409).

Every family covers create, show, list, edit and delete, a show after the
delete returning the not-found message, and the error paths the current
acceptance tests check.

### Isolation and timing

- Every object name is `t-<kind>-<8 hex>`, and every created object has a
  `t.Cleanup` that deletes it through the CLI, so reruns against a kept stack
  never collide. Nothing depends on seed data or on another case.
- A case needing a second actor (ACL enforcement, key rotation, invitations)
  creates its own user or client and writes an extra profile for it.
- `eventually(t, timeout, fn)` retries until the check passes, 30 s for
  search: erchef indexes asynchronously.
- One server per package run; cases run in parallel.

## Section 2: targets

### `integration/cincserverng` (CI)

- `TestMain` starts one `server.New` with orgs `cinccli` and `cinccli-other`,
  signature checks and ACL enforcement on, writes the admin key to a temp
  file, and stops the server afterwards.
- `Gaps`: every entry links an upstream cinc-server-ng issue, filed when the
  case is added, and is removed once that issue is fixed.

### `integration/cincservererlang` (ad hoc)

- Reads `CINC_SERVER_ERLANG_TARGET`, or by default
  `../terraform/.out/target.json`:

  ```json
  {
    "server_url": "https://203.0.113.10",
    "org": "cinccli",
    "other_org": "cinccli-other",
    "admin": "cinccli-admin",
    "key_path": "/abs/path/integration/terraform/.out/admin.pem",
    "ca_cert_path": "/abs/path/integration/terraform/.out/ca.pem"
  }
  ```

- Without the file the test skips with "run
  integration/run-cinc-server-erlang.sh", so CI compiles and lints it without
  contacting AWS.
- Before the suite it polls for up to 20 minutes, until `/_status` answers
  and `cinc org show <org>` succeeds, then points at
  `/var/log/cloud-init-output.log` over SSM on timeout.
- `Gaps` starts empty. erchef is the reference, so a failure is a CLI or
  cinc-api bug until shown otherwise. Entries are allowed only for server
  limitations, such as operations erchef reserves to pivotal, and each states
  what was observed.

## Section 3: Terraform (`integration/terraform`)

The cinc-api stack, reused with its own names:

- Providers `aws`, `tls`, `http`, `local`, `random`, pinned, lock file
  committed, local state only. Defaults: `us-west-2`, `t3.xlarge`, CINC Server
  `15.10.125`, caller's IP /32, prefix `cinc-cli-it`, orgs `cinccli` and
  `cinccli-other`, admin `cinccli-admin`.
- Own VPC, public subnet, internet gateway and route table; security group
  with 443 from the caller only; Ubuntu 22.04 from Canonical's SSM parameter;
  IMDSv2; encrypted gp3 root volume; SSM instance profile; no key pair;
  `terminate` shutdown behaviour; every resource tagged
  `cinc-cli-integration = "true"`.
- Elastic IP allocated first; throwaway CA and server certificate with the
  EIP as an IP SAN; admin RSA key generated locally, only its public half in
  user-data. The package URL and SHA-256 come from omnitruck at apply time.
- Bootstrap: 4-hour self-shutdown; install and verify the package; server
  config with the certificate; `reconfigure`; create the admin with the
  Terraform key, both orgs with the admin associated, and
  `grant-server-admin-permissions`.
- Outputs `.out/admin.pem`, `.out/ca.pem` and `.out/target.json`, mode 0600.

## Section 4: CLI changes, CI, docs, delivery

### `trusted_certs_dir`

knife reads extra CA certificates from `trusted_certs_dir` (default
`~/.chef/trusted_certs`). cinc has only `ssl_verify_mode`, so a server with an
internal CA forces `:verify_none`. Add `trusted_certs_dir` (the same key in
cinc and chef credentials, like `ssl_verify_mode`), defaulting to
`~/.cinc/trusted_certs` and falling back to `~/.chef/trusted_certs`; every
certificate in it is added to the system roots. `cinc config validate`
reports certificates it cannot parse. Documented in `docs/configuration.md`.

### `integration/run-cinc-server-erlang.sh`

As in cinc-api: `terraform init`, `apply`, `go test -count=1 -v
./cincservererlang/`, and a `trap` that destroys on exit; `KEEP=1` keeps the
stack, `destroy` tears a kept one down, `GOTESTFLAGS` narrows the run, and a
leftover check lists anything still carrying the tag after a destroy.

### CI

- `.github/workflows/integration.yml`, triggered by `pull_request`, pushes
  to `main` and `workflow_call`: one job, `Integration (cinc-server-ng)`,
  running `go test -race ./...` in `integration/` through gotestsum, plus
  `terraform fmt -check -recursive` and `terraform validate`.
- `binaries.yml` calls that workflow, and its `binaries` job `needs` it, so a
  tag's release assets are published only after the suite passes against
  that exact commit.
- The lint job runs golangci-lint on the integration module too.
- Dependabot: `gomod` for `/integration` and `terraform` for
  `/integration/terraform`, weekly.
- When `test/acceptance` is removed, the required check
  `Acceptance (cinc-zero)` is replaced by `Integration (cinc-server-ng)` in
  branch protection.

### Docs

- `integration/README.md`: the packages, prerequisites, what the stack
  creates, cost (about $0.17/hour, about 10 minutes a run), `KEEP` and
  `destroy`, debugging over SSM.
- `CLAUDE.md`, the `adding-a-command` skill and an `integration-tests` skill
  (replacing `acceptance-tests`): every command needs a unit test and a suite
  case; gap rules; any change to a request the CLI sends is run against
  cinc-server-erlang before merge.

### Delivery (separate PRs, each on the latest `main`)

1. This design.
2. The module, suite framework, coverage guard with `pending` lists,
   the cinc-server-ng target, the nodes family, CI workflow, release gate,
   Dependabot and Makefile target.
3. `trusted_certs_dir` in the CLI (independent of 2).
4. One PR per family, porting its acceptance tests into the suite, adding the
   cases acceptance never had, filing cinc-server-ng issues for gaps, and
   fixing each CLI bug found in its own PR.
5. The Terraform stack, `cincservererlang` target and run script.
6. The first cinc-server-erlang run; each bug found gets its own fix PR (a
   cinc-api bug is fixed in cinc-api, released, and bumped here).
7. Remove `test/acceptance` and the cinc-zero harness; update `CLAUDE.md`,
   the skills, the Makefile and the required checks.

## Out of scope

- A GitHub Actions workflow for the erlang suite (possible later with OIDC).
- Remote Terraform state; multi-node CINC Server topologies.
- The `supermarket` commands against the public Supermarket.
- Load or performance testing.
